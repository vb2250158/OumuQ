# 人格路由设计

OumuQ 的核心不是“选择一个模型生成音频”，而是“选择一个角色，然后让系统决定怎么说”。

## 路由链路

```text
输入文本
  -> 角色配置
  -> 屏幕语言与语音语言
  -> TTS 引擎
  -> 参考音频
  -> 情绪参数
  -> 异步生成任务
  -> 顺序播放队列
```

## 为什么角色优先

在对话系统里，同一句话由不同角色说出来，可能需要完全不同的处理：

- 角色 A 用中文显示，也用中文发声。
- 角色 B 用中文显示，但语音要用日语。
- 角色 C 适合 Qwen3-TTS。
- 角色 D 适合 IndexTTS2。
- 角色 E 使用 Qwen-TTS-API 这类云端 worker，并在本地私有配置中保存音色 ID。
- 同一个角色在开心、严肃、安慰时应选择不同参考音频。

所以 GUI、Agent 和脚本最好只提交：

```json
{
  "character_id": "my_character",
  "text": "晚上好，今天辛苦了。",
  "play": true
}
```

后续由路由层和 worker 解析具体语言、模型、参考音频和情绪。

## 参考音频匹配

参考音频选择按以下维度评分：

1. 请求里的 `match_patterns` 与索引里的 `match_patterns`。
2. 请求 `emotion_vector` 与索引 `emotion_vector` 的距离。
3. `emotion_tags` 和 `mood` 的重合度。
4. 输入文本与参考台词的相似度。
5. 音频时长是否适合作为 prompt。

如果选中的参考音频太短，可以自动拼接相邻或同情绪片段，生成缓存用 composite prompt。缓存不应写回 `voice-references`。

## 语音与屏幕文字可以不同

角色配置里有两个语言字段：

- `visible_language`：用户在屏幕上看到的语言。
- `speech_language`：TTS 实际输出语言。

例如用户使用中文聊天，但角色语音配置为日语时：

- 屏幕文字：中文，方便用户阅读。
- 语音文本：日语，贴近角色原始口吻。

这两个文本不需要逐字一致，但含义应该一致，角色语气也应一致。

屏幕文字不是普通助手摘要，而是同一角色在屏幕语言里的表达。若语音是日语、屏幕是中文，中文应翻译日语语义并保留角色口吻、称呼、亲疏关系和安全边界。

## 异步生成与顺序播放

聊天场景里，用户不应等待完整音频生成完，但也不应看到尚未成功入队的台词。推荐流程：

1. Agent 先准备语音文本和屏幕可见文本。
2. Agent 把语音文本提交给 worker。
3. worker 立即返回 queued job id。
4. Agent 再显示屏幕可见文本。
5. worker 在后台分句生成。
6. 播放器按提交顺序播放音频。

这样可以同时支持实时对话和批量配音。

## 与绘画模式共用角色

绘画模式可以复用 `character_id`，但读取的是 `visual_profile` 这类已脱敏字段，而不是语音来源字段。

```text
character_id
  -> 语音模式读取 speech_language / tts_engine / voice index / api voice metadata
  -> 绘画模式读取 visual_profile / prompt_profile
```

这样同一个抽象角色可以同时驱动语音和视觉，但公开仓库不会泄露真实音色、私有角色名、参考音频 URL 或私有参考图。

## OumuQ 的隐喻

OumuQ 的“人格证”就是这套路由系统的视觉化表达：

- 腰间的人格证：可用角色和音色配置。
- 抽出的一张证：当前激活的人格。
- 麦克风法杖：生成与播放管线。
- 鹦鹉元素：学习和拟声。
